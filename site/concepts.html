Concepts

Four ideas, from first principles

Each concept follows the same four beats: Tell it plainly, Show it, Do something small, Apply it to a real decision.

1. Large language model

First principle. A language model is a function from a sequence of tokens to a probability distribution over the next token. Everything else is scale and training.
Tell

Text is cut into tokens (word pieces). Each token becomes a vector. A stack of transformer blocks mixes those vectors using attention (which earlier tokens matter) and MLPs (nonlinear transforms). The last layer scores every token in the vocabulary. Pick one, append it, repeat. The numbers inside the blocks are the weights, learned by gradient descent to make real text likely.

Show 
"The capital of France is"
   → tokens        [The][ capital][ of][ France][ is]
   → transformer   (attention + MLP) × N layers
   → next-token    " Paris" 0.91   " a" 0.02   " located" 0.01 ...
   → sample, append, repeat
Do

Run a small open model locally and read the probabilities yourself:

pip install transformers torch
python - <<'PY'
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch
name = "Qwen/Qwen2.5-0.5B"          # any small open model
tok = AutoTokenizer.from_pretrained(name)
m = AutoModelForCausalLM.from_pretrained(name)
ids = tok("The capital of France is", return_tensors="pt")
p = torch.softmax(m(**ids).logits[0, -1], -1)
for s, i in zip(*torch.topk(p, 5)):
    print(f"{tok.decode(i)!r:12} {s:.3f}")
PY
Apply

Because behaviour is "which tokens become likely," changing behaviour means changing those probabilities: with a prompt (cheap, shallow), with data you retrieve (RAG), or with the weights (deep). The rest of this site is about the last option.

2. Closed weights

First principle. If you cannot hold the weights, you rent the behaviour. The owner can change it, filter it or withdraw it at any time.
Tell

With a closed model the vendor keeps the weights on their servers and sells access through an API. You send tokens, you get tokens. The vendor decides the safety policy, the filters, the price, the versions and the data retention. You get convenience and frontier quality; you give up control and inspectability.

Do

Write down three tasks your product needs. Mark each: does a closed API already do it within policy? If yes for all three, you probably do not need to train anything.

Apply

Choose closed weights when you want the best general capability fast and the vendor's policy fits your use. Their guardrails are a feature for most products, and they are not something to engineer around.

3. Open weights

First principle. Publishing the weights hands over the behaviour, including the ability to change it. "Open weights" is not the same as "open source".
Tell

An open-weight model ships its trained numbers (usually as .safetensors files) under a licence. You can run it on your own hardware, fine-tune it and inspect it. Training data and code are often not released, and licences vary: some are permissive (Apache 2.0), some add use restrictions or user-count thresholds. Read the licence before you build on it.

Show 
model-00001-of-00004.safetensors   ← the weights (the behaviour)
config.json                        ← architecture: layers, heads, dims
tokenizer.json                     ← text ↔ tokens
generation_config.json             ← default sampling settings
LICENSE                            ← what you are allowed to do
Do 
huggingface-cli download Qwen/Qwen2.5-0.5B-Instruct --local-dir ./base
cat ./base/config.json | head -30     # read the architecture
cat ./base/LICENSE | head -20         # read the terms
Apply

Choose open weights when you need data to stay on your machines, need a behaviour no vendor will sell you (a domain voice, a narrower or looser refusal policy within the law), or need to control cost at scale. You then own the safety work too.

4. LoRA (low-rank adaptation)

First principle. The change needed to adapt a trained model is much simpler than the model itself, so it can be written with far fewer numbers.
Tell

Full fine-tuning updates every weight, which needs memory for the weights, the gradients and the optimiser state. LoRA freezes each chosen weight matrix W and learns an update ΔW = B·A where B is d × r and A is r × k, with r tiny. A matrix of rank r can only move the model along r directions, but research found that is usually enough to steer style, format and policy. The adapter is a small separate file; delete it and the base model is untouched.

Show 
W   : 4096 × 4096  = 16,777,216 numbers (frozen)
A   :   16 × 4096  =     65,536
B   : 4096 ×   16  =     65,536
A+B                =    131,072   (0.78% of W)

forward:  y = W·x + (α/r)·B·(A·x)
init   :  B = 0  →  the adapter starts as a no-op
merge  :  W' = W + (α/r)·B·A     →  no extra inference cost

See the interactive version on the Architecture page.

Do 
from peft import LoraConfig, get_peft_model
cfg = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                 target_modules=["q_proj","k_proj","v_proj","o_proj",
                                 "gate_proj","up_proj","down_proj"],
                 task_type="CAUSAL_LM")
model = get_peft_model(base_model, cfg)
model.print_trainable_parameters()   # trainable: ~0.5% of total
Apply

Use LoRA when you have a narrow behaviour to teach, one GPU, and want to keep several variants (one adapter per customer, domain or tone) on a single shared base. Use full fine-tuning when you need to teach a lot of new knowledge. Next: the SOP.
